# Belastingaangifte Checker — Domain Glossary

## Terms

**Belastingaangifte**
The Dutch income tax return filed with the Belastingdienst. Single document per tax year. Source of truth for comparison. Amounts are rounded to full euros (no cents).

**Jaaropgave**
An annual statement issued by a financial institution (bank, broker, mortgage provider) summarising a taxpayer's financial position or transactions in a given year. Multiple jaaropgaves may be uploaded per session.

**Institution**
The financial institution that issued a jaaropgave. Detected automatically from PDF content. Classified as one of: `bank`, `broker`, `hypotheek`, `other`.

**Rekeningnummer**
Account number (IBAN or broker account ID) used as the primary key for matching a jaaropgave entry to an aangifte entry.

**Gedekt**
A matched item where the aangifte and jaaropgave share the same rekeningnummer and their amounts match (after rounding both to full euros).

**Jaaropgave ontbreekt**
An item present in the aangifte for which no corresponding jaaropgave was uploaded.

**Niet ingevuld in aangifte**
An item present in an uploaded jaaropgave but absent or zero in the aangifte — a potential oversight by the taxpayer.

**Aandachtspunt**
A substantive flag generated by the analyst. Based on a seeded rule set (see `rules/aandachtspunten.md`) plus open-ended LLM judgment. Each aandachtspunt names the triggering condition and its tax implication.

**Box 1 / Box 2 / Box 3**
The three income boxes in the Dutch tax system. Box 1: work and home ownership. Box 2: substantial interest in a company. Box 3: savings and investments. The aangifte is structured around these boxes.

**Extraction**
The first LLM pass: reading a PDF (sent as a native document block) and returning structured data — institution type, rekeningnummers, and relevant amounts. Results are cached to disk in development (keyed by SHA-256 of the PDF content) to avoid re-extraction during testing.

**Account number normalisation**
The process of reducing a rekeningnummer to a canonical form for comparison: strip whitespace, strip punctuation (dots, dashes), strip leading Dutch label prefixes ("Nummer", "Nr"), lowercase. Implemented in `lib/account-normalizer.ts`. Original formatted account numbers are preserved in all displayed output; normalisation is used only for matching.

**Reconciliation**
The JS-side step between extraction and categorization that matches aangifte entries to jaaropgave accounts. Implemented in `lib/reconciler.ts` (`reconcile()`), which runs two passes: primary matching by normalised rekeningnummer, then secondary matching by amount for entries without a rekeningnummer (wage income, AO insurance premiums) and removal of calculated fields that never have a jaaropgave (e.g. Eigenwoningforfait). Produces three buckets: matched pairs, aangifte entries without a jaaropgave match, and jaaropgave accounts without an aangifte match.

**Categorization**
The TypeScript step after reconciliation that produces the four report categories. Implemented in `lib/categorizer.ts` (`categorize()`). Maps matched pairs to covered items or amount mismatches using a FIELD_AMOUNT_OVERRIDES table for field-to-field mapping (e.g. "dividendbelasting" → `broker.dutchDividendTax`). A ±€1 tolerance is applied before classifying a pair as a mismatch. The unmatched aangifte entries become missingStatement; the unmatched jaaropgave accounts become notFilledIn (zero-balance accounts excluded). No LLM involvement.

**Rule checks**
Deterministic attention points generated from jaaropgave metadata by `lib/rule-checks.ts` (`runRuleChecks()`). Checks for: aflossingsvrij hypotheek (from `metadata.mortgageType`), buitenlands dividend (from `broker.foreignDividend` / `foreignWithholdingTax`), and box 3 saldo boven heffingsvrij vermogen (cumulative balance vs a per-year threshold table). These run independently of the LLM and are prepended to any LLM-generated attention points.

**Analysis**
The second LLM pass: receiving only amount mismatches and annual statements for context, then generating open-ended aandachtspunten. Account matching and report categorization are done before this step. The LLM focuses on judging whether amount differences are real filing errors vs expected lifecycle events, and on flagging non-deterministic issues (e.g. from `rules/aandachtspunten.md`).
